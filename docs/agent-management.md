# Agent management and durable session provenance

The host CLI is moving to the standalone
[ai-bridge-cli repository](https://github.com/numanzahid/ai-bridge-cli) (forthcoming).
This server repository does not ship or install that command. Server startup is
`python -m ai_bridge`, independent of host tooling. Existing external executables
are not removed by server upgrades or uninstall; review those separately.

The server retains `management.py` Sessions, Tasks, start_agent and stop_agent,
plus the MCP agent/session/task endpoints. Native CLIs own their authentication,
history and native origin metadata. Bridge aliases/archive flags remain separate
overlays; task cleanup preserves native history and checks ownership, processes,
mounts and active/uncertain jobs. Task workspaces do not expire automatically.

## Stable read-only contract for ai-bridge-cli

Use the service account and its configured `AI_BRIDGE_STATE_DIR`, default
`~/.local/state/ai-bridge`. For each agent/session pair, the optional record is:

```text
<state_dir>/management/provenance/<sha256(agent + ':' + session_id)>.json
```

The digest is lowercase hexadecimal SHA256 of the UTF-8 string, with no newline.
`agent` is `claude`, `codex` or `cursor`; `session_id` is the exact full UUID,
including its case as reported by the adapter. Partial IDs never select records.
Only the 64-hex-digit `.json` filenames form this session contract. Hidden
`.job-<job_id>.json` files are private internal UUID bindings, not session records;
consumers must ignore them. They also have no automatic expiry.
Example schema:

```json
{
  "schema": 1,
  "agent": "codex",
  "session_id": "11111111-2222-4333-8444-555555555555",
  "origin": "mcp",
  "first_seen": 1792270000.25,
  "job_ids": ["1018-120000-0123456789ab"]
}
```

`first_seen` is Unix epoch seconds (UTC), recording the first durable observation,
including when backfilled; it is not the native chat creation time. It never
changes. `job_ids` contains at most 64 distinct bridge job IDs, in insertion order;
new IDs evict the oldest retained IDs. Reobserving a retained ID is a no-op. A
record is at most 16384 bytes. Readers should validate schema, matching agent and
UUID, `origin`, timestamp and bounded IDs, and ignore unknown future fields.
Unsupported, missing, invalid or unreadable records mean unknown provenance, never
proof of native-only activity. Consumers must be read-only and must not import
server code or infer MCP use from native execution mode, SDK markers or cwd.

`Sessions.enrich` exposes `bridge_origin: "mcp"` when a valid record exists,
otherwise `bridge_origin: null`; invalid/unreadable provenance also adds a
`bridge_provenance_error` diagnostic. Native `origin`, `native_source`, mode and parent
relationships are preserved. MCP origin means the session was generated by a
new MCP turn with no requested resume ID, confirmed by an adapter-observed UUID.
It does not describe current activity or merely being touched by MCP. A direct
native chat later resumed through MCP remains unclassified, even after the
adapter reports the matching UUID. A matching MCP resume may append its job ID
only when that session already has a valid MCP origin record; it preserves
`first_seen` and origin. There is no separate MCP-touched classification.

## Evidence, lifecycle and security

Only server `agent_send` sets the explicit job `invocation_origin: "mcp"` marker.
Local `start_agent` calls default to unmarked. An adapter-observed full UUID is
required. Creating a record additionally requires `requested_session_id: null`;
a requested resume ID, even confirmed by matching adapter output, cannot establish
origin. A resume response with a different UUID cannot create or update provenance.
Generic headless/native direct runs and native `exec`/SDK metadata are never evidence.

The detached runner binds each job to the first valid UUID from a recognized
session event across stdout and stderr: Codex `thread.started`, or Claude/Cursor
`system` with subtype `init` and top-level `result` events. Arbitrary JSON, tool/error events and
conflicting ID fields do not establish origin. Later different UUIDs cannot
create a second origin or replace the canonical ID. The binding is serialized
and persisted before the origin record, so retries and backfill cannot rebind
the job. Output snapshots retain that canonical UUID separately from other text.

The runner persists evidence while a turn is active without subsequent polling.
Refreshing/listing jobs backfills marked active or completed jobs from private
canonical-output snapshots before retention can delete them, using the same
creation-only rule. For older snapshots without a canonical UUID, backfill uses
the first recognized session event in a complete private log of at most 4 MiB;
truncated/dropped output or a parsed ID alone does not suffice.
Resume jobs cannot backfill a missing origin record; the originating new-session
job must still be available to establish it. Failed writes retain the job for
retry and report `provenance_error` in job metadata/output snapshots. Only a
confirmed successful persistence clears that error; a later unavailable or
ineligible observation does not clear it or allow pruning. Refresh persists
errors in job metadata so this protection survives a server restart. Records
without an explicit MCP marker cannot be safely backfilled: older jobs that could
also have come from local management remain unknown. Already expired records
cannot be recovered. There is no attempt to guess from prompts or audit snippets.

Provenance records have no automatic expiry and survive job/log retention and
server restarts. Full server uninstall removes the configured server state,
including provenance. No native histories are rewritten.

Upgrades narrowly migrate an existing owner-owned, real `management` directory
with exact mode 0755 (the old listing-created mode) to 0700. The server opens all
ancestors without following symlinks, requires private state, refuses access or
default ACLs (including unknown ACL status), and uses `fchmod` on the pinned
directory descriptor. This runs before management listing/locking and provenance
access. No other path or mode is migrated, and no permissions are loosened.

State, management and provenance directories must be owned by the service user
and private (0700); records and the writer lock are private regular files (0600),
with hard links refused. Paths are derived solely from validated identifiers.
Directory traversal uses pinned directory descriptors and refuses symlinks in all
components. Readers refuse symlinks, special files, foreign ownership, permissive
modes, oversized files and invalid schemas. Writers serialize with `flock`, write
a bounded private temporary file, fsync it, atomically replace the destination and
fsync the directory. Read-only consumers need no lock because replacement is
atomic; they should apply equivalent no-follow and permission checks. These checks
protect against other accounts; same-user code can forge or erase state and is
inside the trust boundary. Unsafe metadata fails closed rather than gaining an
MCP label; persistence failures do not prevent agent execution or server startup.
